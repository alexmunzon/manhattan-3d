# Playable 3D Manhattan - research and build prompt

29 September 2026

## The practical route

Build the **game first**, with a replaceable city renderer. A playable desktop-browser prototype can start in a small Manhattan district: walk, jump/climb, enter a car, and launch a glider. The uncertain part is not movement or HUD work; it is turning Apple's current 3D Flyover data into a reliable, properly aligned world. Treat that as a time-boxed research spike, not a promised dependency. A full-city polished copy of Thijs's game is much larger than a one-week prototype.

Thijs Simonian's [San Francisco game](https://sf.thijs.gg/) and [original post](https://x.com/cdngdev/status/2091909073038082139) are the reference, not a reusable engine. His replies describe scraping Apple Maps photogrammetry. Inspection of his shipped browser bundle in the earlier research found Three.js plus a custom quantized-triangle renderer, zoom-level tile streaming around the player (observed Z15-Z20 and roughly 470 m default loading radius), OSM road data, and Quaternius car assets. Those implementation details are observations, not a published specification or an open-source pipeline. He mentioned using Codex with GPT-5.6 Sol; that does not mean Codex produced his private converter from a prompt alone. The video shows rooftop running, a blue glider, aerial city views and driving with a speed HUD and minimap. His exact tile scraper/converter and build time are not public in the sources checked. Do not represent either as solved.

The [archived retroplasma Flyover project](https://github.com/retroplasma/flyover-reverse-engineering) (created in 2019) documents manifests, signed tile URLs, C3M v3 mesh parsing and OBJ export. Its Go 1.15 setup and old format are research leads, **not** proof that current Apple tiles export. [SynArchive's lightweight fork](https://github.com/SynArchive/Apple-3D-RE-Lightweight) calls itself a cross-platform fix; [ReverseApple's fork](https://github.com/ReverseApple/flyover-reverse-engineering) calls itself a fixed downloader. Neither was verified end-to-end on Apple's current 3D tiles. Search also returns an “AppleMapDownloader” that stitches **2D raster imagery**, not Flyover 3D meshes. Do not mistake it for a converter. There is no verified current, supported Apple 3D game-data API or public drop-in version of Thijs's pipeline in these sources.

**Legal reality:** [Apple Maps Terms of Use §1.3](https://www.apple.com/legal/internet-services/maps/terms-en.html) expressly restrict copying, extracting and scraping service content, unauthorized caching, and reverse engineering, with a narrow legal exception for the latter. A tiny personal project does **not** make those restrictions disappear. Keeping it private lowers distribution exposure but does not turn extraction into authorized use. Do not publish Apple data, derived meshes/textures or a publicly playable Apple-backed game. If no permission or usable lawful route is established, keep Apple as an unimplemented research result and use the fallback. This is practical risk context, not legal advice.

The documented fallback is [Google Photorealistic 3D Tiles](https://developers.google.com/maps/documentation/tile/3d-tiles), available through the billed Map Tiles API with a key and a compatible renderer such as [CesiumJS](https://developers.google.com/maps/documentation/tile/use-renderer). Google requires visible logo and per-tile data attribution, plus its [Map Tiles API policies](https://developers.google.com/maps/documentation/tile/policies). It is a licensed alternative subject to terms and billing, **not** “zero legal drama.” Review the current EEA terms if used from Spain. Do not ingest Google's geometry to create an offline Apple substitute or derive game objects from its imagery contrary to those policies.

## Paste into your coding assistant

Build a complete working **desktop-browser 3D city game prototype**. Output complete source files and run commands, not merely a plan, pseudocode, TODO placeholders or invented proof that current Apple tiles can be extracted. If you can work in a repo, write and run the project there; otherwise provide every file in filename-labeled fenced blocks. Prioritize a finished, testable small district and a usable game loop over claiming an entire city. Use subagents if available for (1) current Apple format/terms and adapter feasibility, (2) game controls/physics, (3) renderer/coordinates/performance, and (4) independent tests/security review. Give each a bounded assignment, reconcile their findings, and integrate the tested result yourself. If unavailable, do these checks sequentially. A research subagent's assertion is not a working converter.

### Goal and scope

Make a real local desktop-browser game set on Manhattan and its connecting bridges, inspired by Thijs Simonian's San Francisco demo, where I can walk/run, jump and climb an accessible surface, enter/exit and drive a car, and launch, steer and land a hang glider above a recognizable 3D city area. Target **Manhattan only, including the bridges that connect to it**. Begin with a compact Lower Manhattan district and the Brooklyn and Manhattan Bridges if the source covers them; the eventual map may extend along Manhattan and include other Manhattan-connected bridges (for example Williamsburg, Queensboro/Ed Koch and George Washington) to their far-side landings, but do not build the rest of the boroughs. Check actual coverage rather than assuming every bridge has complete 3D mesh. Keep the Manhattan boundary and spawn configurable for development; a missing tile must not expand the shipped scope silently. Keyboard and mouse controls, third-person camera, readable speed/altitude HUD, a minimap with north and player marker, pause/help/reset controls. No phone-only or GamePigeon dependency. No multiplayer, mission system, full city, custom triangle-splat renderer or secret backend in version 1. Mark later ideas as later ideas.

### Phase 0 - Apple data feasibility spike (time box: one focused day; no false green)

1. Research the current Apple Maps terms and current 3D Flyover availability for the selected Manhattan district and connecting bridge corridors. Review the archived retroplasma project and the newer forks above, dates, open issues, supported formats and any present-day reproducible converter. Distinguish a 2D screenshot/raster downloader from actual textured 3D mesh. Record each source URL and date. Do not infer that a GitHub README or a 2022 fork works today.
2. Define an `IWorldSource` interface separating scene loading, coordinate conversion, terrain/height query, collision proxy generation and credit text. Implement an Apple adapter only if there is a source you have permission to use and a verified current extraction/format path. Before any Apple network extraction or storage, surface the exact terms/rights uncertainty and get a decision; do not silently scrape, evade access controls, automate bulk downloads, spoof a client, or publish an extracted dataset. If not established, leave Apple adapter disabled with a precise diagnostic explaining the blocker. Keep the architecture ready to accept user-supplied, rights-cleared 3D meshes without pretending those meshes were obtained.
3. Spike acceptance: written source/rights assessment, a reproducible one-block test **only if authorized**, mesh geometry and textures load with verifiable geographic orientation and scale, memory and fetch count recorded, and no key/data committed. If any gate fails, state which failed and switch to Phase 1 on Google tiles; do not mark Apple support complete. Never use another provider's data and label it Apple.

### Phase 1 - playable world and movement

Use TypeScript, Vite, Three.js for game objects/controls/physics integration, and an appropriate 3D Tiles renderer for the Google adapter (CesiumJS or a proven Three.js-compatible renderer; verify coordinate-space and shared depth/compositing rather than assuming mixing engines works). Pick a maintained lightweight physics/collision library after checking its current API. Keep renderer and world-source code separate from the controller. Google mode reads a local `.env` API key such as `VITE_GOOGLE_MAPS_API_KEY`; `.env` is ignored and `.env.example` contains a placeholder only. Client-side keys are visible in the browser, so restrict the key to the Map Tiles API and intended development origin in Google Cloud, enable billing quotas/alerts, and document that a private `.env` does not conceal it from clients. Show Google's logo and dynamically returned copyright/data-source attributions onscreen, unobscured by HUD. Respect cache/display policies. If no key is present, give a clear setup screen and use a tiny openly licensed or procedurally generated demo block for offline tests; do not disguise it as real photogrammetry.

Start at a known, configurable Manhattan spawn with walkable ground, camera following a human-scale avatar, WASD movement, mouse camera, shift sprint, space jump, and a clear interaction key. Handle pointer-lock release, keyboard focus, reset, loading and tile failure. Use a stable local ENU/world coordinate origin around spawn; convert lat/lon/alt to game coordinates once, consistently for avatar, roads, collision and minimap. Mesh appearance does not imply collision: build a deliberately bounded collision proxy for walkable surfaces and obstacles, and document where it is approximate. Support low-spec graphics mode, bounded tile radius/LOD, unload distant tiles and release GPU memory. Avoid asserting Thijs's ~470 m radius is optimal for this implementation.

Phase 1 acceptance: fresh clone starts locally with documented commands; demo block runs without keys; configured 3D tiles load near the configured Manhattan spawn with accurate visible credits; avatar can move/jump on a bounded surface and cannot fall through it; returning to spawn works; key absent and tile failure show useful errors; memory is stable across repeated short traversals. Verify these behaviors in a real desktop browser and report measured results, not imagined screenshots.

### Phase 2 - game loop

Add a contextual, testable climbing action for selected ledges, with reachable-height and obstruction checks. Add a freely licensed car asset (e.g. [Quaternius](https://quaternius.com/), after checking the selected pack's license) and simple arcade drive physics: enter/exit, steer, accelerate, brake, reverse, collision and recovery. Roads may use [OpenStreetMap](https://www.openstreetmap.org/copyright) when independently obtained and attributed; separate their geometry from visual Apple/Google city meshes, avoid implying OSM credits cover Apple imagery, and do not use Google imagery to trace roads. Add a deployable glider while airborne, steer/bank, speed loss, lift and safe landing. Do not promise physically accurate flight. Smooth camera transitions, HUD state, speed in mph or km/h with label, altitude relative to a documented reference, minimap and control legend. For bridges: prevent driving or gliding through missing spans; show a clear coverage gap and stop at a safe boundary if a bridge has no usable geometry. A small collectable or checkpoint loop is optional only after controls work.

Phase 2 acceptance: a human tester can complete walk -> climb -> enter car -> drive -> exit -> glide -> land -> reset in one run; state transitions do not duplicate controllers or leave a stuck camera; car and glider have distinct control feel; roads/minimap line up at the Manhattan spawn district; HUD values and credits stay readable at desktop width. Capture browser evidence of the actual run and fix collision, z-fighting or camera failures before calling it done.

### Phase 3 - quality and release hygiene

Tests: pure unit tests for coordinate round-trip within an explicit tolerance, controller state transitions, glider deployment/landing, car enter/exit and tile-loader disposal; mocked adapter tests for absent credentials and errors; an opt-in browser smoke test for a single complete loop. Offline tests must not call paid APIs or fetch Apple/Google assets. Add performance instrumentation (FPS, draw calls, loaded tiles and approximate memory), a capped tile radius and graceful quality reduction. Test on current desktop Chrome, and note actual hardware and limits. Never say tests passed unless run.

Code may live in a public GitHub repository **only if it contains no Apple/Google tile bytes, extracted assets, session URLs, credentials, private logs or proprietary shader/code copied from Thijs**. Provide `.gitignore`, `.env.example`, license/attribution inventory, README setup, controls, architecture, limitations, cost/quota warning and exact test/run commands. Default to local development; do not auto-deploy a playable Apple-backed game. README legal note: "Apple's terms restrict scraping, extraction and unauthorized caching; this repository contains no Apple map data. A personal project is not an exemption. Do not publish Apple-derived data or an Apple-backed public game without the necessary rights. Google's optional 3D Tiles mode requires its own terms, billing and on-screen attribution." If rights/permission are unresolved, keep the Apple adapter clearly disabled. No mislabeling a Google demo as Apple support.

Deliver a concise project tree; complete implementation; exact setup, test and run commands; a source/rights/uncertainty table; phase-by-phase acceptance results marked pass, fail or not run; and remaining blockers. If an API or data converter is unverified, say so and ship the playable fallback rather than fabricating an integration. Explain the next smallest step for going from the district prototype to bounded Manhattan-plus-bridges tile streaming, but do not claim a one-day clone of Thijs's renderer.

- [Google Photorealistic 3D Tiles](https://developers.google.com/maps/documentation/tile/3d-tiles), [renderers](https://developers.google.com/maps/documentation/tile/use-renderer), [policies/attribution](https://developers.google.com/maps/documentation/tile/policies), [usage and billing](https://developers.google.com/maps/documentation/tile/usage-and-billing): fallback capability, visible credits, key/billing and quotas.
- [OSM copyright](https://www.openstreetmap.org/copyright) and [Quaternius](https://quaternius.com/): road-data and model leads; check the specific asset license before use.
